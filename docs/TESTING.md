# Проверки DirectLAN 0.3.5

В 0.3.5 проверено сохранение адреса, обнаруженного WireGuard после аутентифицированного входящего пакета, даже если echo и отдельное подтверждение состава не завершились. Тест исключает обновление доверия по одному лишь настроенному адресу и проверяет истечение срока наблюдения. Обновление запроса уже известного участника сохраняет работающий адаптер и сокет.

Тест с настоящими UDP-сокетами и устройствами WireGuard начинает с неверного адреса гостя у владельца: только гость знает правильный адрес владельца и начинает соединение. Затем проверяется roaming, ответ рукопожатия и двусторонняя передача данных с маскировкой и без неё. Отдельно проверены счётчики повреждённых оболочек, повторов control и аутентифицированных пакетов; эти счётчики не открывают разрешений.

Два существующих STUN-провайдера теперь проверяются на одном сокете. Тесты с подставными DNS и ответами проверяют опрос обоих адресатов, дедупликацию, разные наблюдения, отсутствие ответа и общий срок ожидания. Один ответ не считается доказательством типа NAT или достижимости. Реальный отдельный локальный UDP-пробник получил ответ только от одного из двух адресатов; этого недостаточно для вывода об изменении NAT-адреса между адресатами.

Журналы 0.3.4 показали принятые инициации у владельца и отсутствие принятых пакетов у гостя. Это не различает потерю обратного пакета и отказ проверки до счётчика WireGuard. Новые `transport_counters` разделяют общий приём UDP, проверку оболочки, типы WG-пакетов и control. Для обычного UDP счётчики типов относятся к сокету, для маскированного — к аутентифицированной оболочке конкретного пира; это не подтверждение принятия пакета WireGuard. Причину конкретного отказа между удалёнными ПК предстоит подтвердить повторной проверкой.

В 0.3.4 воспроизведена и исправлена ошибка Windows UDP echo: пакет 128 байт вызывал WSAEMSGSIZE и завершал обработчик, после чего корректная проверка не получала ответа. Регрессионный тест с настоящими UDP-сокетами теперь подтверждает ответ на корректный запрос после oversized-пакета. Также проверены обработка WSAECONNRESET/WSAENETRESET, штатное закрытие, повреждённые и неразрешённые запросы.

Проверен двусторонний обмен устройств WireGuard через реальный policyTUN поверх memory TUN и UDP в обычном и маскированном режимах. Дополнительно проверены счётчики пакетов, ошибки записи адаптера, стадии ошибок Probe и отсутствие подмены ответа.

Первичный допуск при неизменном виртуальном IP и ключе владельца устанавливает подписанных пиров без закрытия UDP-сокета и Wintun. Владелец также добавляет нового участника без пересоздания существующих соединений. Тесты транзакций через интерфейс транспорта проверяют успешную установку, частичный отказ, ошибку сохранения и отзыв добавленных разрешений; реальное сохранение NAT-состояния у провайдера требует повторного испытания на двух удалённых ПК. Обновление разрешений уже допущенных гостей с изменением состава пока может пересоздавать их адаптер.

Проверено, что копирование неизменённого кода не повышает версию; свежий аутентифицированный адрес не заменяется устаревшим при неудачной пробе. Служебные ответы обрабатываются отдельно от длительных проверок. Фикстуры UI проверяют работающий пинг при ожидании синхронизации состава, неработающий туннель при наличии рукопожатия, чтение открытого журнала и копирование последних строк.

В 0.3.3 исправлено ожидание допуска после принятия запроса владельцем. Локальные журналы прежней версии содержали только создание Wintun; сохранённый профиль владельца уже включал гостя, а гостевой интерфейс оставался в ожидании подписанного состава. Это подтверждает незавершённый обмен допуском, но не доказывает доступность UDP между провайдерами.

Новый служебный канал проверен на настоящих UDP-сокетах в обычном и маскированном режимах. Тест с двумя устройствами WireGuard подтверждает: служебный обмен проходит, но до допуска у гостя нет установленных пиров WireGuard, рукопожатия и передачи пользовательских данных. Проверены подмена, другая сеть, отражение, повторы, размер и ограниченная очередь.

Тесты допуска проверяют привязку cookie к источнику, участнику, nonce и секрету, фрагментацию, подпись, закреплённого владельца, версию, локальный ключ и назначенный IP. Применение подписанного допуска проверено на приостановленном профиле без создания Wintun. Неверные коды сохраняют прежний профиль. Простое обновление метаданных отделено от изменения разрешений; действующий адаптер при нём сохраняется. Новые журналы показывают этапы допуска, его подтверждение и результат проверки туннеля без записи кодов и приватных ключей.

Локально пройдены go test ./..., go vet ./..., проверка зависимостей, сборка Go Windows x64 и WPF. Проверены SHA-256 архива Wintun и цифровая подпись DLL.

Тест транспорта проверяет три устройства WireGuard через настоящие UDP-сокеты во всех шести направлениях. У каждой пары отдельные ключи. Отдельно проверены повреждение и отражение оболочки, другая сеть, удалённый участник, STUN на том же сокете и предел IPv6/UDP-пакета 1280 байт.

Тесты кодов проверяют подпись владельца, десять уникальных участников, ошибки допуска, подмену подписи, неверные адреса и ключи, неоднозначный JSON и ограничения размера. Проверены сохранность прежнего профиля при ошибке восстановления и отсутствие ложного зелёного статуса после остановки.

Отдельный локальный запуск с правами администратора проверил реальный Wintun. Владелец создал сеть, принял два запроса, оба гостя по очереди установили по два прямых пира и маршруты. Неудачное изменение локального ключа восстановило прежний туннель и маршруты. Временные адаптеры после теста закрыты.

Интерфейс проверен на состояниях владельца, ожидания допуска, нескольких участников и недоступной службы. Пинг отображается отдельно по каждому участнику.

Проверка трёх физических ПК в разных сетях, нагрузка CPU, скорость, поведение провайдеров и восстановление после сна ещё предстоят. go test -race не запускался, поскольку текущая сборка выполняется без CGO.

В версии 0.3.2 проверены сохранение паузы после перезапуска, повторное отключение и ошибки команд без сети. Изолированные процессы проверили повторный запуск окна, освобождение блокировки и восстановление после аварийного выхода. Интерфейс проверен в состояниях паузы, активной сети, ожидания допуска, десяти участников и недоступной службы.
